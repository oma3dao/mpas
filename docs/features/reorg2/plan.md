# MPAS Reorg 2: Static Bridge Generation

**Status:** Implemented  
**Created:** 2026-07-16
**Implemented:** 2026-07-16
**Scope:** Replace the SDK's dynamic bridge factory with a top-level code generator that produces static bridge MCP servers and draft application plugins  
**Goal:** Bridge MCP servers are static, pre-built artifacts — not runtime-generated from plugin config  
**Implementation:** `bridge-generator/`, `examples/demo/src/bridge/github-bridge.ts`, `examples/demo/plugins/github-demo-plugin.json`, and SDK bridge slimming are in place.

---

## 1. Problem

The SDK currently generates an MCP server at runtime by reading a
plugin file and deriving tool definitions from it. This is wrong:

1. **The plugin defines policy, not capabilities.** The plugin says
   which operations are governed by MPAS approval flows. It should
   not determine what tools the bridge exposes.

2. **The agent shouldn't know MPAS exists.** The bridge should look
   identical to the upstream MCP server — same tools, same schemas.
   MPAS interception is transparent.

3. **MCP servers are static.** Real MCP servers (GitHub, Supabase)
   have hardcoded tools. The MPAS bridge should too.

4. **The ecosystem model.** Upstream services will eventually author
   their own MPAS bridges, importing `@oma3/mpas` for primitives.
   A "generic bridge factory" doesn't scale to that world.

The coupling caused a concrete bug: removing `create_issue` from the
plugin (it's pass-through, doesn't need policy) made it disappear
from the bridge's exposed tools. The upstream defines capabilities;
the plugin defines policy. These are independent concerns.

## 3. Target Architecture

Three pieces, cleanly separated:

### 3.1 SDK Libraries (`sdk/protocol/src/lib/`)

Unchanged. These are protocol primitives that any MPAS bridge imports:

- `ActionPackageBuilder` — construct Action Packages from tool calls
- `AdapterClient` — submit to the Credential Adapter
- `CoordinationClient` — handle approval wait/poll loop
- `KeyManager` — signing
- `verification`, `policy-engine`, `plugin-loader` — verifier utilities
- `receipt-builder`, `approval-builder`, `auth-requirements-builder`
- `did-key`, `trace`

**Removed from SDK:** `plugin-tool-generator.ts`, `proposer-bridge.ts`, `cli.ts`

### 3.2 Bridge Generator (`bridge-generator/`)

A top-level package (not inside `sdk/`). Development-time CLI that
spawns a live upstream MCP server, discovers its tools via `tools/list`,
and outputs two artifacts:

1. **Static bridge MCP server** (TypeScript) — hardcoded tools, full
   approval flow, imports `@oma3/mpas` for protocol primitives
2. **Draft application plugin** (JSON) — conforming to the Application
   Plugin Profile spec, containing every discovered upstream tool as a
   reviewable first-pass artifact

**Location:** Top-level `bridge-generator/` directory with its own
`package.json` and `tsconfig.json`.

**Rationale for top-level:** The SDK (`sdk/protocol`) is a runtime
library imported by user code. The generator is a dev-time CLI with
different dependencies (child process spawning, MCP handshake, code
generation). It doesn't belong in a package users `npm install` for
runtime use.

**Publishing:** TBD. Local monorepo tool first.

**Full specification:** `docs/features/reorg2/spec.md`

### 3.3 Example Bridge (`examples/demo/src/bridge/`)

Generated by running the bridge-generator against the demo's upstream
GitHub MCP server, then checked into the repo. Serves as:

- The actual bridge the demo uses (what the agent harness points at)
- A living proof that the generator works
- A reference for what a real MPAS bridge looks like

Exposes: `create_issue`, `delete_branch`, `merge_pull_request` —
matching the upstream exactly.

## 4. Generator Design

See `docs/features/reorg2/spec.md` for the full bridge-generator
specification including CLI interface, MCP discovery protocol, code
generation templates, plugin generation behavior, error
handling, and test scenarios.

Summary:
- Spawns upstream, performs MCP handshake, calls `tools/list`, kills
  the process
- Outputs a static bridge TypeScript file with hardcoded tools and
  full approval flow
- Outputs a draft plugin JSON with all discovered tools, ready for
  human or LLM-assisted refinement
  conforming to the Application Plugin Profile spec
- Works universally with any MCP server over stdio

## 5. Implementation Record

### Phase 1: Build the bridge-generator (`bridge-generator/`) — Done

1. Create `bridge-generator/` with `package.json`, `tsconfig.json`
2. Implement MCP discovery (spawn → initialize → tools/list → kill)
3. Implement bridge code generation (template with hardcoded tools)
4. Implement plugin generation (all operations with
   `executionPayloadSchema` derived from upstream `inputSchema`)
5. Wire up CLI argument parsing
6. Test against `examples/demo/tests/fixtures/adapter/github-mcp-server.mjs`

### Phase 2: Generate the example bridge and wire it up — Done

1. Run bridge-generator against the demo upstream GitHub MCP server
2. Save bridge to `examples/demo/src/bridge/github-bridge.ts`
3. Save plugin to `examples/demo/plugins/github-demo-plugin.json` (or verify
   existing plugin matches)
4. Add to demo's `tsconfig.build.json` so it compiles
5. Update `guides/setup-macos.md` to point agent harness at
   `dist/bridge/github-bridge.js` instead of `sdk/protocol/dist/cli.js`
6. Verify demo tests still pass

### Phase 3: Slim the SDK — Done

1. Remove `sdk/protocol/src/bridges/proposer-bridge.ts`
2. Remove `sdk/protocol/src/cli.ts`
3. Remove `sdk/protocol/src/lib/plugin-tool-generator.ts`
4. Remove their exports from `sdk/protocol/src/index.ts`
5. Rebuild SDK — ensure it compiles and existing tests pass
6. All `lib/` exports remain unchanged

## 7. Constraints

- Don't break existing demo tests (they test adapter, coordination,
  signer-server — not the bridge CLI)
- Bridge config JSON format stays the same (deployed on user machines):
  mode, plugin, adapter.url, agent.did, agent.keyFile,
  target.applicationDid, coordination.url, approvalStrategy,
  approvalTimeoutMs
- SDK `lib/` exports remain unchanged — downstream code depends on them
- Generated bridge handles full approval flow:
  submit → additionalApprovalsRequired → coordinate → wait/poll → resubmit
- Generated bridge exposes exact same tools as the upstream MCP server
- Generated plugin conforms to the Application Plugin Profile spec
  (`specs/mpas-profile-application-plugin.md`)
- Generated plugins initially include all upstream tools. Operations
  that should be pass-through may be removed during review, but the
  generated artifact preserves the complete upstream surface first.

## 9. Design Decisions

| Decision | Rationale |
|----------|-----------|
| Generator at top-level `bridge-generator/`, not inside `sdk/` | SDK is a runtime library; generator is dev-time tooling with different concerns and deps |
| Generator outputs both bridge and plugin | One command scaffolds everything needed to MPAS-enable a service |
| Generated plugin starts with all tools | The first artifact should preserve the whole upstream surface so review cannot silently miss a tool |
| Initial impact metadata is heuristic, no LLM | Zero external dependencies; plugin is small enough to refine manually or with an LLM in a second pass |
| Generated bridge is checked in | It's source code — hand-editable, reviewable, testable |
| Phase ordering: generator → example → slim SDK | Repo stays in working state at every phase boundary |
| No "from-plugin" alternative input mode | If you can't reach the upstream, you have no source of truth for tools. The generator requires a live upstream. |
| Publishing TBD | No need to decide now; it's a monorepo tool first |
| Separate spec.md for the generator | Enables a test engineer to write tests from the spec independently |

---

## 10. Risks

| Risk | Mitigation |
|------|------------|
| Generator output drifts from upstream when tools change | Re-run generator; diff shows exactly what changed |
| Checked-in generated code becomes stale | CI can verify generated output matches current upstream |
| Initial impact metadata misclassifies operations | Impact is informational only; human reviews before check-in |
| Generator adds maintenance burden | It's small; MCP protocol is stable |
| Breaking change to MCP handshake protocol | Generator is the only thing that speaks MCP at codegen time; single fix point |
