# Bridge Generator Specification

**Status:** Implemented  
**Package:** `bridge-generator/`  
**Purpose:** Development-time CLI that produces a static MPAS bridge MCP server and a draft application plugin from a live upstream MCP server  
**Implementation:** `bridge-generator/` generates the demo bridge at
`examples/demo/src/bridge/github-bridge.ts` and first-pass plugin output
for review.

---

## 1. Overview

The bridge-generator is a CLI tool that connects to an upstream MCP
server, discovers its tool definitions, and outputs two artifacts:

1. A TypeScript source file implementing a static MPAS bridge MCP
   server with hardcoded tool definitions
2. A JSON file implementing a draft `MpasApplicationPlugin` document

Both artifacts are checked into source control and edited by hand
as needed. The generator is run once per upstream (or re-run when
the upstream's tool surface changes).

---

## 2. CLI Interface

### 2.1 Command

```sh
npx bridge-generator \
  --output-bridge <path> \
  [--output-plugin <path>] \
  -- <upstream-command> [upstream-args...]
```

### 2.2 Arguments

| Argument | Required | Type | Description |
|----------|----------|------|-------------|
| `--output-bridge` | Yes | string | File path for the generated bridge TypeScript file |
| `--output-plugin` | No | string | File path for the generated draft plugin JSON file |
| `--` | Yes | delimiter | Everything after `--` is the upstream MCP server command and argv |

The `--` form avoids lossy shell re-parsing of quoted upstream
arguments. Example:

```sh
npx bridge-generator \
  --output-bridge examples/demo/src/bridge/github-bridge.ts \
  --output-plugin examples/demo/plugins/github-demo-plugin.json \
  -- node examples/demo/tests/fixtures/adapter/github-mcp-server.mjs
```

### 2.3 Exit Codes

| Code | Meaning |
|------|---------|
| 0 | Success — both outputs written |
| 1 | Argument validation failed (missing required args, invalid paths) |
| 2 | Upstream process failed to spawn |
| 3 | MCP handshake failed (no valid `initialize` response) |
| 4 | `tools/list` request failed or returned no tools |
| 5 | Output file write failed |

### 2.4 Stdout / Stderr Behavior

- Stdout: silent (no output on success)
- Stderr: progress messages and errors
  - `Spawning upstream: <command> <args>`
  - `MCP handshake complete: <serverInfo.name> <serverInfo.version>`
  - `Discovered <N> tools: <tool1>, <tool2>, ...`
  - `Bridge written to: <path>`
  - `Plugin written to: <path>`
  - Error messages prefixed with `ERROR:`

## 3. MCP Discovery Protocol

The generator communicates with the upstream MCP server over stdio
using JSON-RPC 2.0, following the MCP protocol specification.

### 3.1 Process Lifecycle

1. Spawn the upstream process: `<upstream-command> [upstream-args...]`
2. Connect to the process's stdin (write) and stdout (read)
3. Perform the MCP handshake (§3.2)
4. Request tool definitions (§3.3)
5. Kill the upstream process (SIGTERM, then SIGKILL after 5s)

### 3.2 Initialize Handshake

Send:
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2024-11-05",
    "capabilities": {},
    "clientInfo": { "name": "mpas-bridge-generator", "version": "1.0.0" }
  }
}
```

Expect response with:
- `result.protocolVersion` — string
- `result.capabilities` — object (may include `tools`)
- `result.serverInfo` — object with `name` and optional `version`

After receiving the response, send the `notifications/initialized`
notification:
```json
{
  "jsonrpc": "2.0",
  "method": "notifications/initialized"
}
```

**Failure:** If no valid response is received within 10 seconds, exit
with code 3.

### 3.3 Tools List Request

Send:
```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/list"
}
```

Expect response with:
- `result.tools` — array of tool definitions

Each tool definition has:
- `name` — string (required)
- `description` — string (optional)
- `inputSchema` — JSON Schema object (required)

**Failure:** If no valid response within 10 seconds, or `tools` is
empty, exit with code 4.

### 3.4 Process Cleanup

After receiving `tools/list` response:
1. Send SIGTERM to the upstream process
2. Wait up to 5 seconds for exit
3. If still running, send SIGKILL

## 4. Bridge Code Generation

### 4.1 Output Format

The generated file is a self-contained TypeScript module that:
- Is executable as a stdio MCP server
- Has no dependency on the upstream MCP server at runtime
- Imports protocol primitives from `@oma3/mpas`
- Imports MCP SDK types from `@modelcontextprotocol/sdk`

### 4.2 Generated Structure

```typescript
#!/usr/bin/env node
/**
 * MPAS Bridge MCP Server
 * Generated by bridge-generator
 * Upstream: <upstream-command> [upstream-args...]
 * Generated: <ISO timestamp>
 *
 * Tools: <tool1>, <tool2>, ...
 *
 * This file is generated then checked in. Edit freely.
 */

import { readFile } from "node:fs/promises";
import { pathToFileURL } from "node:url";
import { Server } from "@modelcontextprotocol/sdk/server/index.js";
import {
  CallToolRequestSchema,
  ListToolsRequestSchema,
} from "@modelcontextprotocol/sdk/types.js";
import {
  ActionPackageBuilder,
  AdapterClient,
  CoordinationClient,
  KeyManager,
} from "@oma3/mpas";
import type {
  ProposerConfig,
  AdapterResponse,
  ActionReference,
} from "@oma3/mpas";

// ─── Tool Definitions ─────────────────────────────────────────────────────────

const TOOLS = [
  // One entry per discovered tool, verbatim from tools/list
  {
    name: "<tool_name>",
    description: "<tool_description>",
    inputSchema: <tool_inputSchema>,
  },
  // ...
];

// ─── Config ───────────────────────────────────────────────────────────────────

interface BridgeConfig {
  plugin: string;
  applicationDid?: string;
  adapterUrl: string;
  agentKey: string;
  coordinationUrl?: string;
  approvalStrategy?: "return" | "coordinate" | "wait";
  approvalTimeoutMs?: number;
  executionProfile?: { id: string; format: string };
  defaultExpirationMinutes?: number;
}

async function loadConfig(configPath: string): Promise<BridgeConfig> {
  const raw = JSON.parse(await readFile(configPath, "utf8"));
  return {
    plugin: raw.plugin,
    applicationDid: raw.target?.applicationDid ?? raw.applicationDid,
    adapterUrl: raw.adapter?.url ?? raw.adapterUrl,
    agentKey: raw.agent?.keyFile ?? raw.agentKey,
    coordinationUrl: raw.coordination?.url ?? raw.coordinationUrl,
    approvalStrategy: raw.approvalStrategy ?? "wait",
    approvalTimeoutMs: raw.approvalTimeoutMs,
    executionProfile: raw.executionProfile,
    defaultExpirationMinutes: raw.defaultExpirationMinutes,
  };
}

// ─── Bridge Server ────────────────────────────────────────────────────────────

// ... (tool call handler, approval flow, MCP server setup)
// See §4.3 for approval flow specification
// See §4.4 for server lifecycle

export async function runBridge(args = process.argv.slice(2)): Promise<void> {
  // Parse --config, load config, initialize clients, start server
}

if (process.argv[1] && import.meta.url === pathToFileURL(process.argv[1]).href) {
  await runBridge();
}
```

### 4.3 Approval Flow

The generated bridge implements the full MPAS approval flow. For each
tool call:

1. **Build Action Package**
   - Use `ActionPackageBuilder` with config's `applicationDid`,
     `executionProfile`, `keyManager`, `defaultExpirationMinutes`
   - Call `buildFromToolCall(toolName, args)`

2. **Submit to Adapter**
   - Use `AdapterClient` to POST the Action Package
   - Receive `AdapterResponse`

3. **Handle Response**

   | `response.result` | Behavior |
   |-------------------|----------|
   | `executed` | Return execution result to agent |
   | `failed` | Return error or relay execution result |
   | `additionalApprovalsRequired` | Enter coordination flow (step 4) |
   | `rejected` | Return error |
   | `expired` | Return error |
   | `cancelled` | Return error |
   | `malformed` | Return error |
   | `notSupported` | Return error |
   | `policyUnavailable` | Return error |
   | `indeterminate` | Return error (do not retry) |
   | `pending` | Return pending status |
   | Unknown | Return unrecognized-result error |

4. **Coordination Flow** (when `additionalApprovalsRequired`)

   Based on `config.approvalStrategy`:

   - **`return`**: Return immediately with pending status, action ref,
     and authorization requirements
   - **`coordinate`**: Submit to Coordination Service, return
     immediately with coordination action ref
   - **`wait`** (default): Submit to Coordination Service, then poll
     until resolved or timeout

5. **Wait/Poll Loop** (strategy = `wait`)
   - Poll `CoordinationClient.poll(agentDid)` every 2 seconds
   - Look for matching `actionUpdate` by `actionEnvelopeHash`
   - On `readyForResubmission`: resubmit the coordinated Action
     Package to the Adapter, return the terminal result
   - On `cancelled`: return error
   - On `expired`: return error
   - On timeout (`approvalTimeoutMs`, default 300000ms): return
     pending status

### 4.4 Server Lifecycle

1. Parse `--config <path>` from argv
2. Load and parse config JSON
3. Load the Application Plugin from `config.plugin`
4. Derive `applicationDid` and `executionProfile` from the plugin,
   unless explicitly overridden by config special cases
5. Initialize `KeyManager` from `config.agentKey` (file path)
6. Initialize `AdapterClient` with `config.adapterUrl`
7. Initialize `CoordinationClient` with `config.coordinationUrl`
   (if present)
8. Create MCP `Server` with name derived from upstream server info
9. Register `ListToolsRequestSchema` handler → return `TOOLS`
10. Register `CallToolRequestSchema` handler → approval flow
11. Connect `StdioServerTransport`

### 4.5 Tool Definitions

Tool definitions in `TOOLS` are copied verbatim from the upstream's
`tools/list` response:
- `name`: exact string from upstream
- `description`: exact string from upstream (or omitted if absent)
- `inputSchema`: exact JSON Schema object from upstream

No transformation, filtering, or modification. The bridge exposes
the same tool surface as the upstream.

### 4.6 Logging

The generated bridge logs to stderr in JSON format:
```
[mpas-bridge] {"ts":"...","level":"info","msg":"...","key":"value"}
```

Required log points:
- `tool_call_received` — on each incoming tool call
- `submitting_to_adapter` — before adapter submission
- `adapter_response` — after adapter response (include `result`)
- `additional_approvals_required` — when entering coordination
- `submitting_to_coordination` — before coordination submission
- `entering_wait_loop` — when starting poll loop
- `resubmitting_approved_action` — before resubmission
- `resubmission_response` — after resubmission
- `wait_timeout` — when poll loop times out
- Errors: `coordination_not_configured`, `poll_error`

## 5. Plugin Code Generation

### 5.1 Output Format

The generated file is a JSON document conforming to the
`MpasApplicationPlugin` schema defined in
`specs/mpas-profile-application-plugin.md`.

### 5.2 Complete Tool Artifact

The generator includes **every** discovered upstream tool in the
generated plugin's `operations` object.

This first-pass plugin is an artifact of the upstream tool surface:
reviewable, diffable, and safe to refine later. A human, LLM-assisted
review tool, or policy authoring step may later remove pass-through
operations or add richer metadata, but the generator itself does not
attempt to omit tools that look read-only. Losing a tool at generation
time would hide it from later review.

### 5.3 Generated Plugin Structure

```json
{
  "version": "1",
  "type": "MpasApplicationPlugin",
  "pluginDid": "did:web:PLACEHOLDER",
  "pluginVersion": "1.0.0",
  "publisherDid": "did:web:PLACEHOLDER",
  "applicationDid": "did:web:PLACEHOLDER",
  "executionProfile": {
    "id": "did:web:profiles.oma3.org:mcp",
    "format": "mcp.toolsCall"
  },
  "credentialRequirements": [],
  "operations": {}
}
```

### 5.4 Operation Generation

For each discovered tool, generate an operation entry:

```json
{
  "<tool_name>": {
    "description": "<tool_description>",
    "impact": "<inferred_impact>",
    "executionPayloadSchema": {
      "type": "object",
      "required": ["name", "arguments"],
      "properties": {
        "name": { "const": "<tool_name>" },
        "arguments": <tool_inputSchema>
      },
      "additionalProperties": false
    }
  }
}
```

Where:
- `tool_name` — from upstream `tools/list`
- `tool_description` — from upstream `tools/list` (empty string if absent)
- `tool_inputSchema` — the upstream tool's `inputSchema`, used as-is
  for the `arguments` property schema
- `inferred_impact` — see §5.5

### 5.5 Initial Impact Inference

The generator assigns `impact` based on tool name heuristics:

| Pattern (case-insensitive) | Impact |
|----------------------------|--------|
| Name contains `delete`, `remove`, `destroy`, `drop`, `purge` | `"critical"` |
| Name contains `merge`, `deploy`, `release`, `transfer`, `revoke` | `"high"` |
| Name contains `create`, `update`, `modify`, `edit`, `write`, `set`, `add` | `"medium"` |
| All other operations | `"medium"` |

Impact is informational only — it does not affect runtime behavior.
The values are intentionally rough starting points for later review.

## 6. Error Handling

### 6.1 Upstream Spawn Failures

| Condition | Behavior |
|-----------|----------|
| Command not found | Stderr: `ERROR: Failed to spawn: <command>`, exit 2 |
| Process exits before responding | Stderr: `ERROR: Upstream exited with code <N> before handshake`, exit 2 |
| Process crashes during handshake | Stderr: `ERROR: Upstream crashed during handshake`, exit 3 |

### 6.2 Protocol Errors

| Condition | Behavior |
|-----------|----------|
| Invalid JSON on stdout | Stderr: `ERROR: Invalid JSON from upstream`, exit 3 |
| Missing `result` in response | Stderr: `ERROR: Malformed response to <method>`, exit 3 |
| `tools/list` returns empty array | Stderr: `ERROR: Upstream reported zero tools`, exit 4 |
| JSON-RPC error response | Stderr: `ERROR: <method> failed: <error.message>`, exit 3 or 4 |

### 6.3 Output Errors

| Condition | Behavior |
|-----------|----------|
| Output directory doesn't exist | Create it (mkdir -p equivalent) |
| Output path is not writable | Stderr: `ERROR: Cannot write to <path>: <reason>`, exit 5 |
| Output file already exists | Overwrite without prompting |

## 7. Generated Bridge Runtime Behavior

This section specifies the runtime behavior of the generated bridge
(not the generator itself). Test engineers use this to validate
generated bridges.

### 7.1 Startup

1. If `--config` is missing or file doesn't exist → write usage to
   stderr, exit 1
2. If config JSON is malformed → write error to stderr, exit 1
3. If `agentKey` file doesn't exist → write error to stderr, exit 1
4. Otherwise → start MCP server, listen on stdio

### 7.2 Tool Call Handling

For each `tools/call` request:

1. If `name` doesn't match any tool in `TOOLS` → return MCP error
   response (unknown tool)
2. Build Action Package from tool name and arguments
3. Submit to adapter
4. Handle response per §4.3 approval flow
5. Return MCP `tools/call` response

### 7.3 Argument Passthrough

The bridge MUST pass tool arguments through to the Action Package
without modification. It does NOT validate arguments against the
tool's inputSchema — that's the agent's responsibility (and the
adapter validates against the plugin's `executionPayloadSchema`).

### 7.4 MCP Protocol Compliance

The generated bridge MUST:
- Respond to `initialize` with valid server info
- Respond to `tools/list` with the hardcoded `TOOLS` array
- Respond to `tools/call` with valid tool call results
- Ignore unknown methods gracefully (no crash)
- Handle `notifications/initialized` without response

## 9. Constraints

- The generator requires a live, reachable upstream MCP server. There
  is no offline/from-file mode.
- The generator does not validate that the upstream is a "real"
  production server — it works with any process that speaks MCP stdio.
- Generated files are overwritten without prompting on re-run.
- The generated bridge TypeScript file is meant to compile with the
  same tsconfig as the consuming project (ES modules, NodeNext
  resolution).
- The generator itself has no runtime dependency on `@oma3/mpas` — it
  only generates code that imports it.

---

## 10. Dependencies

### Generator (dev-time)
- Node.js (child_process for spawning upstream)
- No external runtime dependencies beyond Node stdlib

### Generated Bridge (runtime)
- `@modelcontextprotocol/sdk` — MCP server and transport
- `@oma3/mpas` — protocol primitives (ActionPackageBuilder,
  AdapterClient, CoordinationClient, KeyManager)
- Node.js stdlib (fs, url)
