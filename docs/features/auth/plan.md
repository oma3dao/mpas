## Dependencies

**RFC 9421:** [`http-message-signatures`](https://github.com/dhensby/node-http-message-signatures) (dhensby) `1.0.6` — standalone general-purpose implementation, post-1.0. Reproduces RFC 9421 B.2.6 byte-exactly. Exposes `createSignatureBase` / `formatSignatureBase` as public API, which both `signMessage` and `verifyMessage` call internally — so signing and verification share base construction.

**Content-Digest:** [`structured-headers`](https://www.npmjs.com/package/structured-headers) `2.0.3` — add as an exact direct dependency in `sdk/protocol/package.json` and pin in its lockfile; RFC 9651/8941 encode/decode. SHA-256 via Node/Web Crypto.

**Ed25519 / keys:** `jose` (existing) + `KeyManager` — already in the SDK. Add a raw Ed25519 signing capability or adapter for RFC 9421 signature-base bytes; retain the existing compact-JWS API for MPAS artifacts. Pass raw sign/verify adapters into the RFC 9421 library.

**Not used:** Cloudflare `web-bot-auth` and its engine `http-message-sig`. Originally named primary; withdrawn after the vector gate failed. Rationale in [`decisions.md` §11](./decisions.md#11-dependency-choice).

**Dependency hygiene:** every package imported by `src/` MUST appear in `sdk/protocol/package.json` `dependencies`. Importing a transitive dependency resolves locally via npm hoisting but breaks under stricter layouts, and `npm pack` cannot detect it — see the Risks table.

## Phase 1: SDK Auth Library

**Area:** `sdk/protocol/src/lib/`

Signing and verification land together — they share signature-base construction and building them apart is how the two sides drift.

- [ ] Commit RFC 9421 Appendix B vectors (B.1.4 key, B.2 `test-request`, B.2.6 ed25519 case) and MPAS signature-base fixtures to `tests/fixtures/` and `conformance/`. Assert byte-exact signature base and signature. **This is the gate** — run it before building anything else. Vectors come from the RFC, never generated by our own implementation ([`decisions.md` §12](./decisions.md#12-conformance-vectors)).
- [ ] Integrate exactly `http-message-signatures@1.0.6` for signature-base construction, `Signature-Input`/`Signature` serialization, Ed25519 sign/verify; pin exactly `structured-headers@2.0.3` for Content-Digest encoding.
- [ ] After switching to dhensby, remove `web-bot-auth` and `http-message-sig` from package manifests and lockfiles.
- [ ] Declare every imported package directly in `package.json`; remove any declared-but-unused entries.
- [ ] Use `structured-headers` for Content-Digest encoding rather than hand-formatting `sha-256=:<base64>:`.
- [ ] Add a raw Ed25519 signing capability or adapter backed by `KeyManager` key material for RFC 9421; do not repurpose `KeyManager.sign()`, whose compact-JWS output remains the MPAS artifact-signing API.
- [ ] Signers omit `alg` (HTTP profile §4.6.2); verifiers accept it when present and equal to `ed25519`.
- [ ] `signMpasRfc9421()` — computes `Content-Digest`, sets `tag="mpas-v1"`, builds `Signature-Input`, signs, returns headers.
- [ ] `verifyMpasRfc9421()` — framework-agnostic, returns authenticated DID or typed failure. No Fastify, no HTTP framework import.
- [ ] `NonceStore` interface + in-memory implementation with an atomic `claim(keyid, nonce, expires)` operation; exactly one concurrent claim succeeds and successful claims remain retained through `expires`.
- [ ] Derive the verification key from `keyid` without resolution (AUTH-04); reject non-`did:jwk` values and embedded private material (AUTH-03), and reject non-Ed25519 keys (AUTH-05).
- [ ] Select exactly one `Signature-Input` dictionary member tagged `mpas-v1` with a matching `Signature` member; accept any label while recommending `mpas`, and reject zero or multiple tagged candidates.
- [ ] Enforce exact covered-component list; reject more or fewer (AUTH-01, AUTH-02).
- [ ] Derive algorithm from DID; reject inconsistent `alg` (AUTH-05).
- [ ] Verify `Content-Digest` against body (AUTH-10).
- [ ] Freshness validation (AUTH-06, AUTH-16); signed-request `audience` comparison (AUTH-09).
- [ ] Typed failure reasons mapping explicitly to feature spec §6 and HTTP profile §§4.8–4.9, while returning generic `signature_invalid` externally for presented-signature failures.
- [ ] Export from `src/index.ts`.
- [ ] Tests: round trip; tampered body/path/key; algorithm substitution; bad `keyid` including embedded private JWK; expired/future/over-long/equal/reversed timestamps; extra/missing covered components; missing required signature parameters; wrong/missing tag; malformed, partial, and ambiguous `Signature-Input`/`Signature` dictionaries; audience mismatch; atomic concurrent `NonceStore` claim and retention.

**Exit:** RFC 9421 B.2.6 passes byte-exact on both signature base and signature bytes. Sign and verify agree on the MPAS profile. Every imported package is declared. Zero framework dependencies are added.

## Phase 2: SDK Client Signing

**Area:** `sdk/protocol/src/lib/coordination-client.ts`

- [ ] `CoordinationClientConfig` gains an optional signer. When absent, it sends unsigned requests compatible with an unenforcing service (AC-11).
- [ ] Sign all four requests via `signMpasRfc9421()` when the existing or lazily resolved `KeyManager` is available; real bridges MUST auto-sign and require no opt-in flag.
- [ ] Derive `audience` only from the configured coordination URL origin and inject it into every signed request body; do not add a separate bridge audience setting.
- [ ] Accept either a `KeyManager` or a lazily-resolved signer (bridges hold a `Promise<KeyManager>`).
- [ ] Differentiate auth failure from outage — distinct error type for 401/403; keep `CoordinationUnavailableError` for transport failures and 5xx.
- [ ] Tests: signed client verifies on all four endpoints; origin derivation handles URL paths, trailing slashes, default and non-default ports, and bracketed IPv6; no signer sends unsigned requests without requiring `audience`; 401 surfaces as auth error; 503 still surfaces as unavailable; unenforcing servers ignore `audience` when present.

**Exit:** Clients with keys sign correctly and derive audience without extra configuration. Unconfigured clients remain compatible with unenforcing services. Auth failure and outage are distinguishable by type.

## Phase 3: Reference Coordination Server

**Area:** `examples/demo/src/coordination/`

The proving ground. Validates both the library and the binding pattern before anything downstream depends on either.

- [ ] Auth configuration: `enforcement`, non-empty audience origin set, `clockSkew`, and configurable `signatureLifetime` constrained to `<= 60s`.
- [ ] Fail closed at startup when enforcement is enabled and the audience set is empty or contains an invalid origin; add startup tests for both cases (AUTH-21, AC-18).
- [ ] Wire `verifyMpasRfc9421()` into `coordination-api-server.ts` on the four protocol routes; leave `/health` open (AUTH-19).
- [ ] Ensure raw body available for digest verification alongside `strictJsonParse`.
- [ ] In-memory `NonceStore` with atomic claim semantics.
- [ ] Identity and authorization invariants, all enforced before processing:
  - `poll`: signature `keyid` equals required v1 `did`; scope to that agreed DID (AUTH-12)
  - `action-cancel`: signature `keyid` equals required v1 `proposerDid`, and both equal the stored proposer (AUTH-13)
  - `action`: signature `keyid` equals `actionPackage.actionEnvelope.proposer.did` (AUTH-14)
  - `approval`: signature `keyid` equals the signer DID decoded from the Approval, and that DID is an eligible signer for the referenced workflow (AUTH-15)
  - reject every mismatch or ineligibility with 403; once identity representations are equal, do not depend on which equal representation is used internally
- [ ] Split combined store validation/mutation operations into a side-effect-free preflight and a commit. On mutating endpoints, perform nonce claim after signature, digest, freshness, audience, identity, authorization, and business preflight validation, then mutate immediately; invalid requests do not consume nonces, exactly one concurrent claim succeeds, and successful claims remain through `expires`.
- [ ] Return generic `signature_invalid` for every presented-signature validation failure and keep details internal.
- [ ] Ensure authentication failures reveal no DID existence or pending-work information (AUTH-23); test externally indistinguishable failures for known and unknown DIDs and for DIDs with and without pending work (AC-21).
- [ ] Redact `Signature`, `Signature-Input`, `keyid`, nonces, and request bodies from application, framework, and error logs (AC-12).
- [ ] Ensure authenticated identity and all auth outcomes remain transport metadata and can never be counted as an Approval (AC-15).
- [ ] Default auth **off** only for the documented reference topology inside the trust boundary (AUTH-20, AUTH-22).
- [ ] Update demo signer-server and proposer paths to sign when auth is enabled.
- [ ] Tests: full workflow with auth on and off; explicit poll `keyid == did`, cancel `keyid == proposerDid == stored proposer`, action `keyid == actionEnvelope.proposer.did`, and approval `keyid == decoded signer DID` success and mismatch cases (every mismatch → 403 before processing); authenticated but ineligible Approval submitter → 403 before storage or counting; unsigned → 401; expired/future/over-long/equal/reversed timestamp rejection; nonce replay and concurrent duplicate mutation → exactly one success; invalid request then corrected request with the same nonce → corrected request succeeds; generic external failures; known/unknown DIDs and DIDs with/without pending work produce indistinguishable authentication failures; log capture proves redaction; auth never changes Approval counts or satisfies Authorization Requirements; two DIDs see only their own data.

**Exit:** Demo runs the complete MPAS flow authenticated with real keys. Library needed no server-specific escape hatches. AC-12, AC-15, and AC-21 are owned and pass here.

## Phase 5: Downstream Hosted Support and Staging

**Repo:** `wivity/mpas-coordination-server` — details in that repo's `docs/features/auth/`.

- [ ] Upgrade to `@oma3/mpas@^0.1.0-alpha.4`.
- [ ] Implement configuration, fail-closed startup, framework hook, identity binding, generic external failures, and logging redaction.
- [ ] Implement a durable Postgres `NonceStore` whose atomic claim works across processes, permits exactly one concurrent mutation, retains successful claims through `expires`, and does not consume nonces for invalid requests; add migration and concurrency/order tests.
- [ ] Implement entitlement evaluation only after authentication (AUTH-26); test failed authentication never reaches entitlement.
- [ ] Ensure failed entitlement returns no DID-scoped data (AUTH-27); test all denial paths.
- [ ] Keep entitlement outcomes outside Approval storage/counting and Verifier authority inputs (AUTH-28); test no entitlement or auth result can satisfy approval requirements.
- [ ] Stage hosted support without changing enforcement on an existing deployment.
- [ ] Run a real staging ingress test through the production reverse-proxy and TLS termination path, covering signature headers, raw body digest, configured origin, and client-visible errors before any enforcement cutover.
- [ ] For every fresh hosted Coordination Service outside the trust boundary, default enforcement on and ensure it is never exposed unenforced.

**Exit:** Hosted support is implemented and staging-verified, including AUTH-26–AUTH-28 and durable nonce semantics. Fresh hosted services outside the trust boundary enforce authentication before exposure. Existing production enforcement is unchanged; CUR-01 and CUR-02 remain open.

## Phase 7: Coordinated Enforcement Cutover

Owned by the downstream repo and applicable to existing deployments. Gate: Phase 5 staging ingress passes and Phase 6 bridges ship before enforcement flips. Fresh hosted Coordination Services outside the trust boundary already enforce authentication before exposure and do not wait for this cutover.

- [ ] Confirm all production callers sign and derive the configured service origin.
- [ ] Flip enforcement in a coordinated deployment and run authenticated production smoke tests through ingress.
- [ ] If an exposed service cannot remain inside the trust boundary during migration, perform bridge and server activation atomically or in a maintenance window; do not run an exposed unenforcing intermediate state.
- [ ] Close CUR-01 and CUR-02 only after the cutover is verified.

**Exit:** Existing deployments enforce only after clients are ready; CUR-01 and CUR-02 close here. Fresh hosted services outside the trust boundary were never exposed unenforced.

## Future Version Consideration (Not Current Scope)

Version 1 remains unchanged: `CoordinationPollRequest.did` and `CoordinationActionCancelRequest.proposerDid` stay required and must equal the signature `keyid` on signed requests. A future request schema version MAY remove these redundant fields only at an explicit version boundary; v1 will not be mutated in place. Migration and versioning details will be decided if a future revision is proposed.

## Risks

| Risk | Mitigation |
|---|---|
| `file:` reference left in committed manifest | Phase 4 re-pins and re-verifies |
| Something works only via dev-tree link | Phase 4 installs the packed tarball in an isolated temporary project and validates runtime imports |
| Demo and production verification drift | Cryptographic verification is shared in the SDK; demo and hosted framework, configuration, ingress, persistence, and mutation integrations are tested separately |
| Shared signature-base bug | RFC 9421 Appendix B vectors, not self-generated — a vector produced by the implementation under test would ratify the bug on both sides |
| Phantom dependency: `src/` imports a package absent from `package.json` | Package inspection alone cannot establish completeness. Compare runtime imports with direct `dependencies`, then install the tarball in isolation and validate imports |
| Hosted ingress alters signed inputs or body bytes | Phase 5 runs a real staging test through the production proxy and TLS path before enforcement |
| Clock skew in containers | `clockSkew` is configurable; `signatureLifetime` remains `<= 60s`; boundary scenarios include the possible server-observed skew extension |
| Enforcement flipped before bridges sign | Existing deployments stage support in Phase 5, bridges ship in Phase 6, and coordinated enforcement occurs only in Phase 7 |
| SDK gains a framework dependency | Verification is a pure function; Phase 4 checks manifest and isolated runtime imports |
| ~~Cloudflare library doesn't match vectors~~ | **Occurred.** `http-message-sig` injects `alg` unconditionally and fails RFC 9421 B.2.6. Switched to dhensby, which passes byte-exact ([`decisions.md` §11](./decisions.md#11-dependency-choice)) |
